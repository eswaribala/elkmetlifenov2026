L5 LAB MANUAL - MANAGED COLLECTION WITH ELASTIC AGENT AND FLEET
================================================================
Lab title: Enroll one Elastic Agent and revise its policy
Environment: Ubuntu/KVM, three-node Elasticsearch cluster, Kibana, Fleet Server
Difficulty: Beginner to intermediate
Recommended lab duration: 60-90 minutes (longer if Fleet Server is not installed)

LEARNING OBJECTIVES
-------------------
By the end of this lab, a participant will be able to:
1. Explain the difference between the Fleet control plane and data ingestion.
2. Confirm Fleet Server, Elasticsearch output, and network prerequisites.
3. Create a dedicated Fleet-managed agent policy in Kibana.
4. Install and enroll exactly ONE Elastic Agent on an Ubuntu VM.
5. Verify the agent is Healthy and that System metrics arrive in Elasticsearch.
6. Revise the policy centrally, without SSH-editing an agent YAML file.
7. Confirm the agent received the new policy and is collecting an added log file.
8. Make a second policy revision and verify data arrives from the revised path.

LAB TOPOLOGY
------------
Administrator / browser
    -> Kibana (Fleet UI, port 5601)
    -> Fleet configuration stored through Elasticsearch

Ubuntu Agent VM
    -- HTTPS :8220 --> Fleet Server (enrollment / policies / health)
    -- HTTPS :9200 --> Elasticsearch node(s) (logs / metrics)

Fleet Server
    -- HTTPS :9200 --> Elasticsearch cluster (management state)

Note: Fleet Server is a separate component. Kibana is NOT Fleet Server.
The Elastic Agent normally sends data directly to Elasticsearch; it does
not send all telemetry through Fleet Server. This lab uses an Elasticsearch
output, not the earlier Filebeat -> Logstash -> Elasticsearch exercise.

----------------------------------------------------------

Fleet Server URL:     https://<FLEET_SERVER_IP>:8220

IMPORTANT PRECAUTIONS
---------------------
- Replace all <...> placeholders. They are NOT literal commands or working IPs.
- Do not use localhost:8220 or localhost:9200 to connect from another VM.
- Use a dedicated test VM, ideally not an Elasticsearch data node.
- Only ONE Elastic Agent service may be installed per host. Check first.
- If Filebeat already reads the same files, avoid duplicate data by using
  the unique lab folder /var/log/elastic-l5/.
- Keep enrollment tokens, passwords and service tokens private. Do NOT put
  real tokens in slides, screenshots, shared manuals or public chat.
- Keep the fleet-server certificate and the Elasticsearch CA certificate
  distinction clear: they may be two different CAs.
- The --insecure option shown below is ONLY for an isolated lab using a
  Fleet Server self-signed certificate; not for production deployment.
- Align Elastic Agent with a version supported by your current Fleet Server
  and Elasticsearch cluster. Copy the exact download/install command from
  YOUR Kibana installation rather than guessing a version.

PART 1 - VERIFY THE EXISTING LAB (10 MINUTES)
=============================================

STEP 1.1 - Confirm Elasticsearch is available
On the Ubuntu VM where you already have access to Elasticsearch:

    sudo systemctl status elasticsearch --no-pager

If you are on a dedicated agent VM, Elasticsearch need not be installed
there. Use a network test instead:

    curl -vk https://<ES_NODE_1_IP>:9200

Expected: an HTTPS response (perhaps HTTP 401 Unauthorized). HTTP 401
means the HTTPS endpoint is reachable but authentication is required;
it is not a network failure.

If your cluster uses a private CA, prefer a trusted CA check:

    curl --cacert /path/to/elasticsearch-http-ca.crt \
         -u elastic https://<ES_NODE_1_IP>:9200

Enter the password interactively. The CA certificate must be copied to
this VM if this command is run remotely. Avoid curl -k in production.

STEP 1.2 - Open Kibana
In the browser:

    http://<KIBANA_IP>:5601

Sign in as an administrator or a user with Fleet and Integrations 'All'
privileges. Use the Kibana global search box to find 'Fleet' if it is
not visible in the side navigation.

STEP 1.3 - Verify Fleet Server exists
Kibana -> Management -> Fleet -> Agents

Expected: at least one Fleet Server agent with Healthy status.

If your Fleet Server is already Healthy, SKIP Part 2.
If no Fleet Server exists, COMPLETE Part 2 before enrolling an agent.

STEP 1.4 - Verify Fleet Settings
Kibana -> Management -> Fleet -> Settings

Under 'Fleet Server hosts', confirm the reachable URL is:

    https://<FLEET_SERVER_IP>:8220

Under 'Outputs', inspect the default Elasticsearch output. Example:

    https://<ES_NODE_1_IP>:9200

Provide a trusted Elasticsearch CA / SHA-256 CA fingerprint for this
output if your cluster uses a private CA. If an HA output is configured,
multiple Elasticsearch URLs may be listed. Save changes if required.

Avoid 127.0.0.1 or localhost in Fleet settings when the agent is on a
different VM. An unreachable or untrusted output can make the agent
appear enrolled but prevent ingestion.

STEP 1.5 - Test connectivity from the planned agent VM
On the Ubuntu machine which will run the Elastic Agent:

    hostname -I
    ip route
    curl -vk https://<FLEET_SERVER_IP>:8220/api/status
    curl -vk https://<ES_NODE_1_IP>:9200

The -k switch is for a connectivity test ONLY. A response (including
401/403 from an authenticated service) is more useful than connection
refused/time-out. Use a valid CA for ongoing trusted communication.

Optional TCP check:

    nc -vz <FLEET_SERVER_IP> 8220
    nc -vz <ES_NODE_1_IP> 9200

Install netcat only if needed:

    sudo apt update
    sudo apt install -y netcat-openbsd

PART 2 - ONLY IF FLEET SERVER DOES NOT EXIST (15-25 MINUTES)
===========================================================

Do NOT install another Fleet Server if one is already running.
Recommended: use a separate Ubuntu VM dedicated to Fleet Server.
Do NOT install a second Elastic Agent on an existing Elastic Agent host.

STEP 2.1 - Choose a Fleet Server VM and determine its reachable IP:

    hostname -I

STEP 2.2 - In Kibana, go to Fleet -> Agents -> Add Fleet Server.

STEP 2.3 - For an isolated classroom lab, choose Quick Start.
Enter a name such as L5-Fleet-Server and the URL:

    https://<FLEET_SERVER_IP>:8220

Select Generate Fleet Server policy.

STEP 2.4 - Select Linux and copy the EXACT generated download,
extract and installation commands. Run on the Fleet Server VM.
These commands contain the Fleet Server service token; keep it secret.
Use the package version suggested by your own Kibana / Elastic Stack.

STEP 2.5 - Allow TCP 8220 if Ubuntu firewall rules block it:

    sudo ufw status
    sudo ufw allow 8220/tcp

Only run the allow command if UFW is active and your lab requires it.
On production networks, restrict access to known agent subnets.

STEP 2.6 - On the Fleet Server VM, verify service and listening port:

    sudo systemctl status elastic-agent --no-pager
    sudo elastic-agent status
    sudo ss -lntp | grep ':8220'

STEP 2.7 - In Fleet -> Agents, check Fleet Server becomes Healthy.
Then recheck Fleet -> Settings as shown in Step 1.4.

Note: Quick Start creates a self-signed Fleet Server certificate. An
agent enrolling with this lab configuration may need --insecure. If
using a CA-signed Fleet Server certificate, use --certificate-authorities
instead. Configure the Elasticsearch output CA independently.

PART 3 - CREATE A NEW AGENT POLICY (5 MINUTES)
=============================================

STEP 3.1 - Kibana -> Fleet -> Agent policies.

STEP 3.2 - Click 'Create agent policy'.

Fill in:
    Name:        L5-Ubuntu-Managed-Collection
    Description: Single Ubuntu agent for L5 policy revision lab
    Namespace:   default (or a dedicated lab namespace)

STEP 3.3 - Enable collection of System logs and metrics if the UI
presents this option. Click Create policy.

STEP 3.4 - Open the new policy and confirm that the 'System'
integration is present. If missing, use Add integration -> System,
select this EXISTING agent policy, then Save and continue.

STEP 3.5 - Record baseline evidence:
    Policy name: _______________________________
    Policy revision before changes: ___________
    Integrations listed: _______________________

To see the currently delivered policy later, use Fleet -> Agents ->
selected agent -> Actions -> Maintenance and diagnostics ->
View agent policy (labels vary slightly by version).

PART 4 - ENROLL EXACTLY ONE ELASTIC AGENT (10-15 MINUTES)
=======================================================

STEP 4.1 - Use ONE Ubuntu target VM such as an unused training VM,
Ubuntu Server A, or another server intended to be monitored.

Check for an existing installation before proceeding:

    command -v elastic-agent || true
    systemctl list-unit-files | grep -i elastic-agent || true
    sudo systemctl status elastic-agent --no-pager

If Elastic Agent is already installed and enrolled, do NOT run install
again. Instead use Fleet -> Agents -> Assign to new policy, or use an
unused VM to perform the fresh enrollment exercise.

STEP 4.2 - In Kibana -> Fleet -> Agents -> Add agent.

Choose:
    Agent policy: L5-Ubuntu-Managed-Collection
    Enrollment:   Enroll in Fleet
    OS:           Linux
    Architecture: x86_64 or arm64, matching your VM

STEP 4.3 - Copy the displayed Linux commands from Kibana.
The download URL, version and enrollment token are generated for YOUR
cluster; do not reuse a sample token from a manual.

The commands normally have this general structure:

    curl -L -O https://artifacts.elastic.co/downloads/beats/elastic-agent/elastic-agent-<VERSION>-linux-x86_64.tar.gz
    tar xzvf elastic-agent-<VERSION>-linux-x86_64.tar.gz
    cd elastic-agent-<VERSION>-linux-x86_64

These are TEMPLATES. Use the exact commands provided by your Kibana UI.

STEP 4.4 - Run the installation command shown by Kibana. For a secure
Fleet Server using your own CA, the structure is:

    sudo ./elastic-agent install \
      --url=https://<FLEET_SERVER_IP>:8220 \
      --enrollment-token=<YOUR_POLICY_ENROLLMENT_TOKEN> \
      --certificate-authorities=/path/to/fleet-server-ca.crt

For a Fleet Server set up with Quick Start/self-signed certificate in a
TRUSTED, ISOLATED LAB ONLY, use the generated command with --insecure:

    sudo ./elastic-agent install \
      --url=https://<FLEET_SERVER_IP>:8220 \
      --enrollment-token=<YOUR_POLICY_ENROLLMENT_TOKEN> \
      --insecure

IMPORTANT: --insecure disables verification of the Fleet Server
certificate. It does NOT fix a bad Elasticsearch output CA setting.

If prompted to install, enter Y. This creates and starts the
elastic-agent system service.

STEP 4.5 - Verify the agent service and components on Ubuntu:

    sudo systemctl status elastic-agent --no-pager
    sudo elastic-agent status
    sudo elastic-agent version

Expected:
    elastic-agent service: active (running)
    Elastic Agent state: Healthy / running

STEP 4.6 - Return to Kibana -> Fleet -> Agents.
Locate the Ubuntu hostname. Confirm:
    Status: Healthy
    Policy: L5-Ubuntu-Managed-Collection
    Host:   your agent VM hostname
    Last activity/check-in: recent

Take screenshot #1: Agent enrolled and Healthy.

PART 5 - VERIFY BASELINE COLLECTION (5-10 MINUTES)
=================================================

STEP 5.1 - Open Kibana -> Discover.
Select the 'metrics-*' data view (create it if absent).
Set time picker to Last 15 minutes.

Try the following KQL filter:

    data_stream.dataset : "system.cpu"

Optional additional filter:

    host.name : "<YOUR_AGENT_HOSTNAME>"

Expected: recent CPU metrics from the enrolled Ubuntu agent.
You can also inspect datasets for system.memory or system.network.

STEP 5.2 - In Kibana -> Dev Tools -> Console, try:

    GET _data_stream/metrics-system.cpu-*

Expected: one or more system.cpu metric data streams, assuming
collection has started and the data output is configured correctly.

STEP 5.3 - If your policy collects System logs, check 'logs-*' and
try data_stream.dataset : "system.syslog". Some Ubuntu systems use
journald and may not have /var/log/syslog; absence of syslog events
does not necessarily mean the agent itself is unhealthy.

Take screenshot #2: System metrics in Discover or dashboard.

PART 6 - POLICY REVISION #1: ADD CUSTOM LOG COLLECTION (15 MINUTES)
==================================================================

PURPOSE: Verify that modifying the policy in Kibana starts a new input
on the installed Elastic Agent WITHOUT reinstalling or editing the
agent's local elastic-agent.yml file.

STEP 6.1 - On the Ubuntu agent VM, create a dedicated readable log file:

    sudo install -d -m 755 /var/log/elastic-l5
    sudo touch /var/log/elastic-l5/l5-initial.log
    sudo chmod 644 /var/log/elastic-l5/l5-initial.log

Generate enough content for modern Filestream fingerprinting:

    for i in $(seq 1 45); do
      echo "L5_INITIAL event=$i level=INFO source=ubuntu message=initial_fleet_policy_lab timestamp=$(date -Is)"
    done | sudo tee -a /var/log/elastic-l5/l5-initial.log >/dev/null

Check size (aim for significantly more than 1024 bytes):

    wc -c /var/log/elastic-l5/l5-initial.log
    sudo tail -n 3 /var/log/elastic-l5/l5-initial.log

STEP 6.2 - In Kibana, open:
    Fleet -> Agent policies -> L5-Ubuntu-Managed-Collection

STEP 6.3 - Click Add integration.
Search for 'Custom Logs (Filestream)'. Select it and Add integration.

NOTE ABOUT VERSIONS:
The available integration package and exact field names depend on your
Elastic Stack version. A newer package may require a newer Kibana/Agent.
Use a compatible package version shown in your own Integrations UI.
If Custom Logs (Filestream) is not available, see Part 9 (fallback).

STEP 6.4 - Configure the new integration policy:
    Integration policy name: L5-Custom-Log-Collection
    Log file paths:        /var/log/elastic-l5/l5-initial.log
    Dataset name:          l5demo (if prompted)
    Namespace:             default (or the chosen lab namespace)
    Target agent policy:   L5-Ubuntu-Managed-Collection

You may find the target policy under 'Existing hosts' or
'Where to add this integration', depending on your Kibana version.

STEP 6.5 - Save and continue / Save integration.
This action updates the managed agent policy and automatically pushes
it through Fleet Server to enrolled agents.

STEP 6.6 - Open Fleet -> Agents -> your Ubuntu agent.
Check for agent status changes, policy application activity and the
current policy revision. Allow a short time for the new input to start.

For the rendered policy, try:
    Agent details -> Actions -> Maintenance and diagnostics ->
    View agent policy

Confirm the custom log path appears in the delivered configuration.

STEP 6.7 - Verify new collection in Kibana Discover.
    Data view: logs-*
    Time range: Last 15 minutes
    KQL: message : "L5_INITIAL"

Optionally search:
    data_stream.dataset : "l5demo"

Expected: lines containing L5_INITIAL from the Ubuntu agent. The
actual data stream is usually logs-<dataset>-<namespace>; inspect
the document's data_stream.* fields rather than assuming a name.

STEP 6.8 - Add one MORE event to demonstrate ongoing collection:

    echo "L5_INITIAL event=after_policy level=INFO message=collecting_without_reinstall timestamp=$(date -Is)" | \
      sudo tee -a /var/log/elastic-l5/l5-initial.log >/dev/null

Refresh Discover and search for collecting_without_reinstall.

Take screenshot #3: Policy includes the new Custom Logs integration.
Take screenshot #4: L5_INITIAL data in Discover.

PART 7 - POLICY REVISION #2: CHANGE THE FILE PATH (10 MINUTES)
============================================================

PURPOSE: Demonstrate a true policy REVISION by changing an existing
integration setting and observing data from a NEW file.

STEP 7.1 - Create a SECOND file on the SAME Ubuntu agent VM:

    sudo touch /var/log/elastic-l5/l5-revised.log
    sudo chmod 644 /var/log/elastic-l5/l5-revised.log

Generate test events:

    for i in $(seq 1 45); do
      echo "L5_REVISED event=$i level=INFO source=ubuntu message=policy_path_updated timestamp=$(date -Is)"
    done | sudo tee -a /var/log/elastic-l5/l5-revised.log >/dev/null

STEP 7.2 - In Kibana:
    Fleet -> Agent policies -> L5-Ubuntu-Managed-Collection
    Locate L5-Custom-Log-Collection
    Actions (three dots) -> Edit integration

STEP 7.3 - Change the file path FROM:

    /var/log/elastic-l5/l5-initial.log

TO:

    /var/log/elastic-l5/l5-revised.log

Leave the dataset and selected agent policy unchanged.
Save integration changes.

STEP 7.4 - In Fleet -> Agents -> Ubuntu agent, confirm the new policy
is being applied and then the status returns to Healthy. Compare the
policy revision with the value recorded at Step 3.5 or Part 6.

STEP 7.5 - Verify the new source data:
    Discover -> logs-* -> Last 15 minutes
    KQL: message : "L5_REVISED"

Expected: documents containing L5_REVISED and policy_path_updated.

STEP 7.6 - Optional negative test:
Append a unique line to the OLD file after the new policy is active:

    echo "L5_OLD_AFTER_SWITCH message=should_not_be_collected timestamp=$(date -Is)" | \
      sudo tee -a /var/log/elastic-l5/l5-initial.log >/dev/null

After waiting for the policy to apply, search Discover for:

    message : "L5_OLD_AFTER_SWITCH"

Expected: no NEW event from the old path, provided no other collector
is reading that file. Existing historical L5_INITIAL events remain in
Elasticsearch; a policy change does NOT delete previously indexed data.

Take screenshot #5: New path visible in the integration settings.
Take screenshot #6: L5_REVISED events present in Discover.

PART 8 - EXPLAIN AND REVIEW THE CONTROL FLOW
============================================

1. Administrator edits the policy in Kibana Fleet UI.
2. Fleet stores and manages the updated policy via Elasticsearch.
3. The Elastic Agent checks in with Fleet Server over HTTPS/8220.
4. Fleet Server delivers the revised policy to the agent.
5. Elastic Agent reconciles/starts/stops its integration components.
6. The log collection component reads the configured Ubuntu file.
7. The collected events are shipped to Elasticsearch over the
   configured output, normally HTTPS/9200 in THIS lab.
8. Kibana Discover queries the indexed events and displays the data.

KEY CONCEPTS
------------
Enrollment token: Used to join an Elastic Agent to a selected policy.
Agent policy:    Central definition for configuration and integrations.
Integration:     Specifies which source and dataset to collect.
Fleet Server:    Distributes policy and monitors agent check-ins/status.
Elastic Agent:   Runs collection components on the monitored machine.
Elasticsearch:   Stores the resulting logs and metrics in data streams.
Kibana:         Management, investigation, dashboards and Discover.

PART 9 - TROUBLESHOOTING AND VERSION-SAFE FALLBACK
==================================================

Problem A: Fleet Server absent / port 8220 connection refused
    - Verify Fleet Server is Healthy in Kibana.
    - On Fleet Server: sudo systemctl status elastic-agent --no-pager
    - Check sudo ss -lntp | grep ':8220'
    - Verify correct IP (NOT localhost) and firewall routing.

Problem B: Agent install reports x509: certificate signed by unknown authority
    - For production: use the Fleet Server CA with
      --certificate-authorities=/path/to/fleet-server-ca.crt
    - For Quick Start self-signed classroom lab only, add --insecure.
    - Verify the Fleet Server DNS/IP matches the TLS certificate.

Problem C: Agent enrolled but Unhealthy / no data in Elasticsearch
    - Check Fleet -> Settings -> Outputs -> Elasticsearch URLs.
    - Verify the output CA or trusted CA fingerprint.
    - Agent VM must reach Elasticsearch port 9200.
    - Check sudo elastic-agent status
    - Inspect agent logs:
          sudo journalctl -u elastic-agent -n 100 --no-pager
    - Use Fleet -> Agents -> agent -> Logs (if monitoring is enabled).

Problem D: Integration cannot be installed
    - Check Kibana Internet access to https://epr.elastic.co:443.
    - Verify integration package minimum Kibana / Agent version.
    - Use a version supported by your current cluster.

Problem E: Custom file events do not appear
    - Confirm exact configured path and Unix file permissions.
    - Confirm files are >1024 bytes for modern Filestream defaults.
    - Confirm the agent's policy is updated and Healthy.
    - Check logs-* data view / Last 30 minutes / KQL wildcard.
    - Verify that document timestamps fall inside the time filter.
    - Check data_stream.dataset and data_stream.namespace values.
    - Ensure the agent can read the source; if running with reduced
      permissions, allow the service account appropriate read access.
    - The log file must be on the AGENT VM, not just on Kibana VM.

Problem F: Agent already installed on selected Ubuntu host
    - Never run a second installation on the same host.
    - In Fleet -> Agents select the existing host -> Assign to new policy
      (if permitted); OR use an unused VM.
    - Preserve existing policies if other lab exercises rely on them.

FALLBACK WHEN CUSTOM LOGS (FILESTREAM) IS UNAVAILABLE:
    - Keep the System integration on L5-Ubuntu-Managed-Collection.
    - Fleet -> Agent policies -> this policy -> Settings.
    - Change Agent monitoring from metrics-only to BOTH logs and metrics,
      or change the agent logging level from info to debug temporarily.
    - Save changes, verify the agent received a new policy revision,
      and check Fleet -> Agent -> Logs / status.
    - Reset logging level to info after the exercise to avoid extra
      volume. This proves central policy revision even if a custom
      Filestream package cannot be installed on your Elastic version.
