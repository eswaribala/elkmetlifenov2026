------------------------------------------
Step 4.1 — verify each Elasticsearch VM IP
------------------------------------------

Run on node01, node02 and node03 respectively. Record the hostname and the current address rather than trusting an old VM snapshot:

    hostname
    hostname -I

Expected: node01 = .227, node02 = .246, node03 = .102. If an address differs, update the Fleet output hosts and the rest of this manual to match the LIVE IPs.


--------------------------------------------------------
Step 4.2 — test Elasticsearch from the support/Kibana VM
--------------------------------------------------------

    curl -vk https://192.168.122.227:9200
    curl -vk https://192.168.122.246:9200
    curl -vk https://192.168.122.102:9200

An HTTP 401 response usually proves that HTTPS networking works and authentication is required. Connection timeout/refused or TLS handshake errors need diagnosis. The -k flag is only for a connectivity probe.


-----------------------------------------------
Step 4.3 — inspect Elasticsearch CA and version
-----------------------------------------------

Run on node01; the source CA path was used in your prior Elasticsearch installation:

    sudo ls -l /etc/elasticsearch/certs/http_ca.crt
    sudo openssl x509 -in /etc/elasticsearch/certs/http_ca.crt \
      -noout -fingerprint -sha256
    sudo openssl x509 -in /etc/elasticsearch/certs/http_ca.crt \
      -noout -fingerprint -sha256 | cut -d= -f2 | tr -d ":"

Record the last line (hex SHA-256 CA fingerprint). This is an option for Fleet → Settings → Outputs → Elasticsearch CA trusted fingerprint. Use it only when the endpoints present certificate chains signed by this CA; otherwise configure the correct CA(s).

In Kibana → Dev Tools → Console, run:

    GET /
    GET _cluster/health
    GET _cat/nodes?v

Expected: three nodes available. Do not infer Elasticsearch version solely from the Filebeat package version.


-------------------------------------------------------
Step 4.4 — test routing from node02 to the support host
-------------------------------------------------------

    ip route get 192.168.1.162
    curl -I --max-time 10 http://192.168.1.162:5601
    # If Kibana uses TLS instead:
    curl -kI --max-time 10 https://192.168.1.162:5601

If access fails, diagnose the VM bridge/NAT routes, local firewall and the address exposed by the Kibana VM. Do NOT replace an address with localhost for inter-VM communication.

-------------------------------------------------
Step 8.1 — make sure node02 has no existing agent
-------------------------------------------------

Log in to node02 with SSH or VM console; do not run the new installation on the Kibana support host.

----------------------------------------------------------
Step 8.2 — use Kibana-generated Linux installation command
----------------------------------------------------------

Kibana → Fleet → Agents → Add agent → Choose the existing L5-Ubuntu-Managed-Collection policy → select Linux (x86_64 if applicable). Copy the exact download, extract and install commands for your current Elastic Stack version. General structure:

    curl -L -O https://artifacts.elastic.co/downloads/beats/elastic-agent/\
    elastic-agent-<VERSION>-linux-x86_64.tar.gz
    tar xzf elastic-agent-<VERSION>-linux-x86_64.tar.gz
    cd elastic-agent-<VERSION>-linux-x86_64

The URL line above is schematic; use the unbroken URL that Kibana actually provides. Never use <VERSION> literally.


-----------------------------------------------
Step 8.3 — enroll in the reachable Fleet Server
-----------------------------------------------

If your Fleet Server was set up on 192.168.1.162 with a lab self-signed certificate, this is the expected command structure (paste your real token only in the terminal):

    sudo ./elastic-agent install \
      --url=https://192.168.1.162:8220 \
      --enrollment-token=<YOUR_L5_POLICY_TOKEN> \
      --insecure

Use --insecure only for an isolated, trusted classroom lab. For a trusted Fleet CA, omit --insecure and instead pass --certificate-authorities=/path/to/fleet-server-ca.crt. If Fleet Server is elsewhere, replace the --url with the actual Fleet Server URL shown in Fleet → Settings. Only the enrollment token generated for the L5 policy should be used.

10  Policy revision #1 — add a custom log input
===============================================


----------------------------------------------
Step 10.1 — create a unique test log on node02
----------------------------------------------

    sudo install -d -m 755 /var/log/elastic-l5
    sudo touch /var/log/elastic-l5/l5-initial.log
    sudo chmod 644 /var/log/elastic-l5/l5-initial.log
    for i in $(seq 1 50); do
      echo "L5_INITIAL event=$i level=INFO host=node02 timestamp=$(date -Is)"
    done | sudo tee -a /var/log/elastic-l5/l5-initial.log >/dev/null
    wc -c /var/log/elastic-l5/l5-initial.log

The file should be larger than 1024 bytes because modern Custom Logs (Filestream) uses fingerprint-based file identity by default.


-----------------------------------------
Step 10.2 — create the integration policy
-----------------------------------------

  Kibana → Fleet → Agent policies → L5-Ubuntu-Managed-Collection → Add integration.

  Find Custom Logs (Filestream). Select a package compatible with your running Kibana/Agent version.

  Name the integration policy L5-Custom-Log-Collection.

  Set log file path /var/log/elastic-l5/l5-initial.log and dataset l5demo (if the field is presented).

  Choose namespace default and the existing L5-Ubuntu-Managed-Collection agent policy.

  Save and continue. Do not reinstall or restart the agent simply to apply this change.

VERSION NOTE: The current Custom Logs (Filestream) package documentation lists newer releases requiring Kibana 9.4+. Install the compatible package version exposed by your Kibana, and avoid blindly upgrading a working cluster for this exercise.
